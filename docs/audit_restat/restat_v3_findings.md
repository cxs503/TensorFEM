## 1. 这一层补的是什么

AUDIT-RESTAT 此前三层（11-11 首批 73 份同 sha 交付 / m22264 校准单 / m22304 v2 快照锁定）
都在**同一份自述元数据**上做统计：`mission.result` 里的 `changed_files`、`on_disk_changes`、
`pr_gate`。三层把这份元数据内部的一致性问题（口径未锁、记账缺失、锚点占位串）查得很透，
但**没有任何一层打开仓库**。本层把每单自述清单当「宣称」，去 `/srv/tensor/workspace/<repo>`
的 HEAD 全路径清单逐条核对，得到「宣称 → 落地」矩阵。

不评价正确性（那是 tests/gate 的事），只回答：**报过账的文件，现在还在仓库里吗？**

读法上的三条对比（§3.1）：

- **源码 vs 根目录脚本**：`src` 类 59.1% 存活，根目录一次性脚本（`post_report_*.py` 等）44.0%
  —— m22264 校准单用「脚本冒充实现」扣分的经验判据，在仓库层得到同向佐证。
- **证据工件基本不入库**：`artifacts/outputs/runs/figures` 类条目 58,358 条，存活 **7.0%**。
  故「报告里有数」与「仓库可复现」是两件不同的事：引用历史精度数字前，先确认证据文件是否在库。
- **清单里 18.9% 是 worktree 绝对路径**（48,142 条）：这是「该文件从未进入版本控制」的直接证据，
  而非脏数据。工具对这类条目仍做了「剥掉 worktree 前缀」的严格比对，避免把「后来以相对路径
  合并」误判为丢失。

## 3. 历史探针：merged 却 0 存活的单，进过主干吗？

对 50 单（等距抽样，条件 `pr_gate=merged` ∧ 0 存活）逐条宣称路径跑
`git log --name-only --diff-filter=AM`（`--all` 与 `HEAD` 各一次），路径级归因：

| 路径判定 | 路径数 | 占比 |
|---|---:|---:|
| landed_then_removed（主干历史有 ⇒ 入库后被删/替换） | 574 | 78.6% |
| branch_only（只在 agent 分支） | 0 | 0.0% |
| never_existed（任何历史都没有） | 156 | 21.4% |

任务级：**仅 4.0%（2/50）** 的样本在主干历史里毫无踪迹。

**这条结果否定了我实现前的假设**（「`merged` 章是空的」）：主干历史证明确实落过地。
所以这批亏损的主因不是"假记账"，而是 **落地后消失**——文件曾在主干出现、现在不在 HEAD。
可能机制（未证实，明示为假设）：后续任务的分支以陈旧 base 合并导致回退、显式清理、
或改名（本探针 `--no-renames`，改名会被记成"消失"）。判定归属需要逐条
`git log --diff-filter=D -- <path>` 的删除提交归因，本单未做（列为后续项）。

## 4. 局限（honest）

1. 清单是 agent 自述：本层只核「写进去的」，不核「没写的」，故落地率是**宣称精度的下界口径**。
2. 存活 ≠ 正确：路径命中不说明内容来自该单、也不说明测试通过；内容级归属需 `git log -S`/blame，未做。
3. 同名假阳性：争夺路径（被 ≥2 单宣称的相对路径）占存活条目 51.2%，这是存活率的假阳性上界；
   `basename_only` 弱证据单列、未混入严格存活。
4. HEAD 时点：逐仓 sha/日期记于 JSON `repo_heads`；镜像由 `mirror_ff.sh` 每 15 分钟追平，
   快照后合并的交付不计入存活（保守方向）。
5. 历史探针 `-n 4000` 截断 + `--no-renames`：极早历史与改名会漏判，方向偏保守/偏"never"。
