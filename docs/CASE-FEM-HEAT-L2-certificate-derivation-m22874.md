# CASE-FEM-HEAT-L2 — making the certificate a *derived* artifact (reopened PR#1113)

**Scope.** The deliverables of PR#1113 (`benchmarks/verified/fem_heat_conduction_l2/`,
`src/tensorfem/heat_conduction_l2.py`, `tests/test_heat_conduction_l2.py`) already landed on
`main` via #963 and were amended by #1012 (m20995, the norm-measurement correction). This note
does not re-ship them: it re-verifies them on today's `main` and repairs two defects the
re-verification exposed in the *evidence chain*, not in the physics.

## 1. Decision

| | |
|---|---|
| **Decision** | Should the shipped ARE artifact set stay hand-maintained next to the numbers, or become a machine-derived, machine-checkable function of `run.py`? |
| **Alternatives** | **(A)** status quo — README maintained by hand, no reproducibility gate; **(B)** derive `README.md` from the two JSON artifacts and add a read-only reproduction gate (`run.py --check`). |
| **Hypothesis** | Under (B) the artifact set is reproducible bit-for-bit on the same checkout, and every shipped gate verdict is recomputable by the platform's own auditor; under (A) both claims are unenforced. |
| **Chosen** | (B). Decided before looking at any drift number; the predeclared thresholds below were fixed first. |

## 2. Baseline: two real defects on `main`

**D1 — the README had already drifted from its own numbers.** The file states "Everything below
is regenerated by `run.py`; no number here is typed by hand", but `run.py` never wrote it and no
test read it. Consequence, measured on the committed tree:

| artifact | `generated_at` |
|---|---|
| `result.json` (committed) | `2026-11-16T04:01:26.636964+00:00` |
| `gates_verified.json` (committed) | `2026-11-16T04:01:26.640216+00:00` |
| `README.md` footer (committed) | `2026-11-14T21:58:16.080427+00:00` |

The prose stamp named a run ≈1.3 days older than the JSON committed beside it — a provenance
claim that no longer referred to any shipped artifact. Every table value was still correct, which
is exactly why nothing noticed: the failure mode is silent.

**D2 — one gate was not machine-checkable.** `l2_finest_order_in_band` shipped the prose operator
`"<= and >= 1.95 2.1"` with a single scalar `threshold: 2.1`. `tools/verified_anchor_audit.py`
evaluates only scalar comparisons, so it recorded the gate as unverifiable:

| auditor field | baseline (pre-change) | after m22874 |
|---|---|---|
| `gates_passed` (recomputable) | 7 / 8 | **8 / 8** |
| `gates_unrecomputable` | 1 | **0** |
| `recomputed_overall` | `null` | **`true`** |
| `warnings` | `W_OPERATOR_ABSENT`, `W_FAILED_GATES_LIST_UNCHECKED` | `[]` |

A verdict a reader cannot recompute from the JSON is a claim, not evidence — and the anchor was
overall *certified* on 7 verifiable gates plus one that could not be checked.

## 3. What changed (and what deliberately did not)

* `run.py` renders `README.md` from `result.json` + `gates_verified.json` (`render_readme`); the
  ladder table, gate table, mean order, H₁ orders, Roache residual and cross-check residual are
  all interpolated from the JSON, never typed.
* `run.py --check` is a **read-only** reproduction gate: it re-renders the README from the
  committed JSON, re-hashes the two figures against `result.json`, re-runs the whole ladder and
  compares numbers, and re-derives every gate verdict.
* The band `[1.95, 2.10]` on the finest-pair order is now carried by two scalar gates:
  `l2_finest_order_le_2p1` (upper) and `l2_pair_order_ge_1p95` (lower, whose `min` runs over
  every asymptotic pair and therefore bounds the finest pair too). No acceptance criterion was
  relaxed, added or dropped: the conjunction is the old band. Proof that the lower bound is still
  enforced is a test (`test_band_lower_bound_survives_the_operator_split`).
* **Not changed:** the kernel, the manufactured solution, the mesh ladder, the norms, and all
  eight thresholds. The numbers after the change are identical to the committed ones (see §4), so
  this is a bookkeeping repair, not a re-tuning. No threshold was touched after seeing results.

### Predeclared tolerances (fixed before the measurements)

| quantity | criterion | rationale |
|---|---|---|
| numeric drift, committed vs fresh | ≤ `1e-12` relative | a bitwise claim would only hold on one BLAS build; 1e-12 is two orders below the sixth printed digit, so any drift able to change a published digit still fails |
| gate verdicts | identical, no tolerance | a flipped PASS/FAIL is never a rounding question |
| `README.md` | byte-identical to its rendering | derivation is an equality, not a tolerance |
| volatile fields (`generated_at`, `elapsed_seconds`, `sha256`, `environment`) | excluded from the comparison, checked separately | they record *when*/*where*, not *what* |

## 5. Error judgement against the benchmark

The case is code *verification* against a manufactured harmonic solution, so the reference is exact
and the comparison is discretisation error, not measurement:

| key quantity | reference | value | error | < 3 %? |
|---|---|---|---|---|
| L₂ relative error, 64×64 (gate metric) | exact field `sin(πx)sinh(πy)/sinh(π)` | 1.755209e-04 | 1.76e-04 | **yes** (0.018 %) |
| observed L₂ order, finest pair | theory 2.0 (Q4, `adaptive_poisson_2d` a-priori table) | 1.999854 | −1.46e-04 | **yes** (0.007 %) |
| observed H₁ order, worst asymptotic pair | theory 1.0 | 0.999717 | −2.83e-04 | **yes** (0.028 %) |
| Roache power-law residual | 0 for an exact O(h²) ladder | 1.350864e-04 | 1.35e-04 | **yes** |
| independent recomputation (numpy/scipy, no `tensorfem` import) | kernel L₂ | 4.421566e-11 relative | — | **yes** |
| quadratic-form conservation `max|K·T − f|` | 0 | 1.221245e-15 | — | **yes** |

No key quantity exceeds 3 %; the largest is the L₂ error itself at 0.018 % of the exact field.

## 6. Caveats and limits

* The `1e-12` drift tolerance is a *same-checkout* claim. On a different BLAS/LAPACK build the
  re-run may legitimately move in the last bits; `--check` would then report a drift of order
  1e-15…1e-13, still below the tolerance, but a hostile toolchain could exceed it. The gate is
  designed to catch *physics* drift, and it was only demonstrated on this host.
* `climate`/`environment` and figure `sha256` are excluded from the numeric comparison (they vary
  with interpreter and matplotlib versions); the figure binding is checked separately by hashing
  the committed PNGs, so a stale plot is still caught.
* m20995's own report (`docs/CASE-FEM-HEAT-L2-norm-measurement-defect-m20995.md`) quotes the *old*
  gate id `l2_finest_order_in_band`; that document is a dated record of the state before this
  change and was intentionally left as written.
* Registry bookkeeping: `benchmarks/verified/anchor_certificates.json` and
  `docs/verified-anchor-certificate-table.md` were updated for **this anchor only** (record +
  two aggregate counters, taken from the auditor's own output). A full
  `tools/verified_anchor_audit.py --write` sweep in this checkout additionally reclassifies two
  unrelated anchors (`fem_sent_j_integral`, `fem_thermal`: `E_ARTIFACT_UNTRACKED` →
  `E_ARTIFACT_MISSING`) — pre-existing drift, deliberately not bundled into this change.
